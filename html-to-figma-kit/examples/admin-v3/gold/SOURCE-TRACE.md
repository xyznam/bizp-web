# 원천 → 디스크립션 추적 (골드 스탠다드)

`gold/main/`(01 회원 현황)의 디스크립션이 **어느 원천에서 어떻게 나왔는지** 한 줄기로 보여준다. 새 화면군에서 같은 추적을 할 수 있는지가 원천 슬롯 배정이 제대로 됐는지의 시험이다.

슬롯 정의는 [../../../spec/description-rules.md](../../../spec/description-rules.md) §5, 도출 절차는 [../../../spec/policy-mapping.md](../../../spec/policy-mapping.md) §2.

## admin의 슬롯 배정

| 슬롯 | 문서 |
|---|---|
| A. 화면 원천 | `prototype/admin-v3-static/01_회원현황.html` |
| B. 요구사항 | `planning/38_admin_requirements.md` |
| C. 공통 정책 | `planning/37_admin_operation_policy.md` + `35_admin_common_principles.md` |
| D. 미결 대장 | `planning/39_open_items.md` |
| E. IA | `planning/beeple_admin_IA_launch_v3.xlsx` |

## 1. B(요구사항) → `requirements` 배열

**원문** (`38_admin_requirements.md` → `### 01 회원 현황`)

```
| # | 요구사항 | 판정 | 근거 요소 |
| R1 | 문의한 회원을 즉시 찾는다 | ✅ | 이름·이메일·연락처 검색, 역할·자격·상태 필터 |
| R2 | 회원의 권한 구조(어느 매장, 무슨 역할, 승인 권한)를 즉시 답한다 | ✅ | 보유 매장 권한·연결 매장 컬럼 → 50 상세 |
| R3 | 휴면 계정을 복구한다 | ✅ | 복구 모달(본인 확인 절차 포함) |
| R4 | 셀프 가입이 불가한 회원을 대행 등록한다 | ✅ | `+ 회원 직접 등록` → 53 |
| R5 | 권한 보유 규모를 파악한다 | ✅ | OWNER·업체 자격 지표(필터형) |
| —  | `탈퇴 회원` 지표 | ✂ | 섹션 1 참조 |
```

**산출** (`main/description.json`)

```jsonc
"requirements": [
  { "id": "R1", "text": "문의한 회원을 즉시 찾는다" },
  … R2~R5
]
```

**적용된 규칙**

- 판정 기호(✅)와 `근거 요소` 열은 옮기지 않는다
- **✂ 과잉 후보 행은 요구사항이 아니므로 제외.** 대신 빨강 ※행으로 승격했다(아래 3번)
- `근거 요소` 열은 옮기지 않되 **어느 번호 행에 배정할지를 알려주는 지도**로 쓴다. R1 → 조회조건 행, R5 → 지표 행

## 2. A(화면) → 번호 행 불릿

**원문** — 화면의 `.filter-bar` 안 실제 마크업 (`<option>`, `checked`, placeholder)

**산출** (3번 행 `조회조건`)

```
보유 역할 : 전체 | 대표(OWNER) | 매니저(MANAGER) | 편집자(EDITOR) | 조회자(VIEWER) (default : 전체)
자격 : 전체 | SOHO | 대행사 | 프랜차이즈 | 업체 소속(대행사/프랜차이즈) (default : 전체)
검색어 : 이름 / 이메일 / 연락처 검색. 조회 조건 and 검색 (R1)
```

**적용된 규칙**

- 선택지는 **추측하지 않고 실제 `<option>`에서 읽는다**. 기본값은 `selected`/`checked`에서
- 열거는 `|`, 기본값은 `(default : …)`
- `이름·이메일·연락처`(38 원문) → `이름 / 이메일 / 연락처` — 가운뎃점 금칙(§2-1)
- 요구사항 ID를 `(R1)`로 병기 — **좌표성 ID라 유지**(§4-2)

## 3. D(미결) → 빨강 ※행

**원문** (`39_open_items.md`)

```
| OP-04 | 01 `탈퇴 회원` 지표 제거 | P2 위반(다음 행동 없음) — 이견 가능 판정 | 38 ✂ |
```

**산출** — 빨강 ※행 + 해당 번호 행의 빨강 불릿, **두 곳에**

```jsonc
// flags
{ "kind": "confirm", "text": "'탈퇴 회원' 주요지표 제거 승인 대기 (OP-04, P2 위반, 이견 가능 판정). …" }

// rows[2] "주요지표 (KPI 4종)" 의 불릿
{ "text": "'탈퇴 회원' 지표는 제거 승인 대기 (OP-04). 승인 시 KPI 3종으로 축소", "color": "red" }
```

**적용된 규칙**

- 상태 이모지는 옮기지 않고 **요지 + OP ID만**
- 화면 특정 영역에 걸리는 미결은 ※행에 더해 **그 번호 행에도 빨강 불릿**을 둔다. ※행만 두면 어느 요소 이야기인지 독자가 못 찾는다
- 원천 문서에 명시된 `원천 미정`은 그대로 승격 (OP-31 본인 재인증)

## 4. C(공통 정책) → 검정 ※행

**산출**

```jsonc
{ "kind": "common", "text": "LNB/상단바/목록 공통 동작은 35 공통 원칙(P1~P12), 37 운영 정책서 적용. 개인정보 마스킹/열람 사유 기록(P6) 포함" }
```

**적용된 규칙** — 공통 정책 전문을 매 화면에 복사하지 않는다. **1줄 참조로 처리하고 정의 본체는 General 보드**([../../../spec/general-boards.md](../../../spec/general-boards.md)).

## 5. 타 화면 위임 → 초록

**산출**

```jsonc
{ "kind": "reference", "text": "회원 상세는 50 화면이 정본(행 내 이름 링크), … 부속 보드 : 휴면 복구 BZP-AD-PP-001-01, 열람 동의 BZP-AD-CP-014. … 규칙 정본은 General BZP-AD-GN-007 참조" }
```

**적용된 규칙**

- 다른 화면이 정본인 기능은 여기서 정의하지 않고 **위임 사실만** 적는다
- 부속 보드 Screen ID를 명시 — 독자가 따라갈 좌표
- **공통 팝업(`BZP-AD-CP-014`)은 화면별 보드를 만들지 않고 공통 보드 1개를 참조.** 13화면에 동일 주입되는 팝업을 화면마다 복제하면 보드가 12개 늘어난다

> ⚠ 이 초록 ※행은 현행 규칙에서 **축약 대상**이다. 초록 ※행은 `진입 경로`와 `부속 보드 목록`만 담고, 타 화면 위임과 General 참조는 해당 번호 행의 초록 불릿으로 내리는 것이 이후 관찰에서 나온 방향이다(잠정). 이 골드는 그 이전 상태다

## 6. 콜아웃 ↔ Num 1:1

디스크립션의 모든 번호 행은 디자인 영역의 콜아웃과 1:1로 맞는다.

| Num | title | callout |
|---|---|---|
| 1 | 페이지 헤더/전역 액션 | `region` `.page-h` |
| 1-1 | [가려진 정보 보기] 버튼 | `item` `.pii-btn` |
| 1-2 | [+ 회원 직접 등록] 버튼 | `item` `.btn.btn-primary` (side: right) |
| 2 | 주요지표 (KPI 4종) | `region` `.kpi-row` |
| 3 | 조회조건 | `region` `.filter-bar` |
| 4 | 회원 목록 | `region` `.tbl-wrap` |
| 4-1 | [복구] 버튼 (휴면 행 전용) | `item` `#rowDormant1Actions` (side: right) |

**셀렉터는 전부 IR 트리에 실재한다.** 하나라도 없으면 보드 빌드가 경고를 내고 그 콜아웃이 누락된다. 이것이 진입 판정에서 기존 디스크립션의 콜아웃 보유율을 보는 이유다([../../../workflow/entry-triage.md](../../../workflow/entry-triage.md)).

영역(`region`)은 화면의 큰 구획, 요소(`item`)는 그 안의 개별 컨트롤. `1` → `1-1` → `1-2` → `2` 순서가 표의 출력 순서이자 화면 위→아래 순서다.
